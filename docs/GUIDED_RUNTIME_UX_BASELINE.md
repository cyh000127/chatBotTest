# Guided Runtime UX Baseline

## 1. 목적

이 문서는 메신저 기반 구조화 입력 런타임의 UX 개편 기준을 정의한다.

핵심 목표는 아래와 같다.

- 단계형 입력 런타임과 대화형 표면 사이의 mismatch를 줄인다.
- rule-first 구조를 유지하면서도 사용자가 `어디까지 왔는지`, `지금 무엇을 해야 하는지`, `왜 막혔는지`를 즉시 이해하게 만든다.
- fallback, retry, restart, handoff를 단순 오류 응답이 아니라 복구 UX로 재정의한다.

## 2. 문제 정의

현재 런타임은 자유 대화형 엔진이 아니라 state-aware structured interaction이다.

이 구조 자체는 유지해야 하지만, 아래 UX 문제가 쉽게 발생한다.

- 사용자는 채팅처럼 보이는 표면에서 자유문장을 기대한다.
- 내부 런타임은 current step 기준 parser와 validator를 우선 적용한다.
- 결과적으로 사용자는 `왜 이 문장이 안 되는지`, `지금 버튼만 가능한지`, `텍스트로 입력해도 되는지`를 명확히 받지 못하면 답답함을 느낀다.

따라서 UX 개편의 목적은 자유 대화 엔진으로 바꾸는 것이 아니라, 구조화 입력 런타임이 더 예측 가능하고 덜 답답하게 느껴지도록 표면을 재구성하는 것이다.

## 3. 핵심 UX 원칙

### 3.1 현재 단계 가시성

모든 구조화 플로우는 사용자가 아래를 즉시 이해할 수 있어야 한다.

- 현재 진행 중인 작업
- 현재 단계
- 이미 입력된 값
- 아직 남은 값

권장 표면:

- 진행 배너 또는 짧은 상태 라벨
- 현재 draft 요약
- 다음 질문 1개

예시:

- `비료 입력 3/5`
- `현재 입력: 비료 유형 완료, 제품명 입력 대기`

### 3.2 버튼 단계와 텍스트 단계의 명시적 구분

모든 단계는 아래 둘 중 하나를 분명히 밝혀야 한다.

- 버튼 전용 단계
- 텍스트 입력 허용 단계

강제 원칙:

- 버튼 전용 단계에서는 자유문장을 애매하게 받지 않는다.
- 텍스트 입력 허용 단계에서는 허용 형식 예시를 짧게 함께 준다.
- fallback은 항상 현재 단계의 입력 모드를 다시 알려준다.

예시:

- `이 단계에서는 아래 버튼으로만 선택할 수 있어요.`
- `제품명은 텍스트로 입력할 수 있어요. 예: 표준 복합비료`

### 3.3 retry는 재설명이 아니라 복구 안내다

retry 문구는 같은 안내문 반복이 아니라, 실패 이유와 다음 입력 방법을 짧게 알려줘야 한다.

좋은 retry는 아래를 포함한다.

- 왜 실패했는지
- 지금 가능한 입력 형식
- 바로 누를 수 있는 버튼 또는 예시
- 필요하면 현재 값 1개만 다시 보여주고 새 값만 입력하게 만든다

나쁜 예:

- `다시 입력해주세요.`

좋은 예:

- `사용일은 날짜만 입력할 수 있어요. 예: 2026-05-06, 오늘, 어제`

### 3.4 intro 반복 최소화

처음 진입 시점과 retry 시점의 copy는 달라야 한다.

- 첫 진입: 작업 목적과 현재 질문을 보여준다.
- retry: 긴 설명 없이 무엇이 틀렸고 무엇을 보내야 하는지만 보여준다.

강제 원칙:

- 동일 단계에서 반복 실패가 날 때 intro를 매번 다시 붙이지 않는다.
- retry copy는 첫 진입 copy보다 짧아야 한다.
- retry가 특정 값 재입력 단계라면 전체 draft를 다시 읽게 하지 않고 `현재 값 1개 + 새 값 입력` 패턴을 우선 사용한다.

### 3.5 unknown은 종료가 아니라 guided recovery다

unknown 입력은 `이해하지 못했습니다` 한 문장으로 끝내지 않는다.

항상 아래 셋 중 하나로 회수한다.

- 현재 단계 재안내
- 현재 작업 기준 관련 버튼 제안
- restart, help, support 같은 안전한 탈출 경로

### 3.6 restart와 재진입은 기능 일부다

restart, resume, handoff 이후 복귀는 예외가 아니라 기본 UX다.

사용자는 언제든 아래를 이해할 수 있어야 한다.

- 지금 이전 작업을 이어서 할 수 있는지
- 같은 요청을 다시 제출해야 하는지
- 운영 검토로 넘어갔는지
- 지금 안전하게 돌아갈 수 있는 버튼이 무엇인지

## 4. 플로우별 우선 개선 대상

### 4.1 비료 입력 / 수확량 입력

- 진행 상태 표시를 추가한다.
- 단계별 입력 모드를 명확히 구분한다.
- confirm 직전과 수정 단계에서 현재 draft를 짧게 보여준다.
- retry 문구를 step-aware copy로 세분화한다.

### 4.2 자기 조회 / 농지 바인딩

- 위치 공유, 코드 입력, 후보 선택을 하나의 플로우처럼 보이게 연결한다.
- 위치 실패나 후보 불일치 시 현재 가능한 대안을 바로 보여준다.
- `/myfields`는 단순 목록이 아니라 `현재 등록 상태 + 다음 행동`을 보여줘야 한다.
- 위치 후보가 없으면 고유 번호 입력 단계로 자연스럽게 전환하고, retry 문구는 `위치 실패 설명 + 새 고유 번호 입력` 중심으로 짧게 보여준다.
- 고유 번호 재입력 시에는 등록 방법과 직전 입력 고유 번호만 요약하고, 전체 요약은 다시 반복하지 않는다.

### 4.3 input resolve / reminder 재진입

- `나중에 다시`와 `이어서 진행`의 차이를 명확히 설명한다.
- resume token 기반 재진입은 내부 구현이 아니라 사용자 액션으로 이해되게 문구를 다듬는다.
- unresolved 상태는 운영 검토와 사용자의 다음 행동을 함께 보여준다.
- 후보를 찾지 못한 상태에서는 `다시 입력`, `나중에 다시`, `운영 검토`를 버튼으로 먼저 보여준다.
- `다시 입력`을 선택하면 candidate 설명을 반복하지 않고 `현재 target/method/raw input + 새 값 입력` repair prompt로 돌아가야 한다.

### 4.4 증빙 제출

- 위치 선행, document 업로드, 검증, 재제출, 운영 검토 승격을 단계형으로 분명히 보여준다.
- 파일 형식 오류, 메타데이터 부족, 위치 충돌은 서로 다른 실패 사유로 안내한다.
- 재제출 시 `같은 요청 이어서 제출`이라는 맥락을 유지한다.

### 4.5 지원 이관

- 지원 이관은 `상담 연결 완료`처럼 보이면 안 된다.
- 같은 대화창에서 후속 답변이 이어진다는 점을 명확히 알려야 한다.
- 이관 대기 중에도 `추가 설명`, `처음으로`, `도움말` 같은 안전 액션을 유지한다.

## 5. UX 개편 체크리스트

새 구조화 플로우를 추가하거나 기존 플로우를 수정할 때 아래 항목을 확인한다.

- 현재 단계가 사용자에게 보이는가
- 입력 방식이 버튼 전용인지 텍스트 허용인지 보이는가
- 실패 이유가 구체적으로 드러나는가
- retry 문구가 첫 진입 문구보다 짧고 명확한가
- 현재 draft 또는 이미 입력한 값이 필요한 시점에 보이는가
- restart, back, cancel, help, support 중 안전한 탈출 경로가 있는가
- handoff나 manual review 이후 사용자가 다음 상태를 이해할 수 있는가

## 6. telemetry 기준

UX 개편은 copy 수정만으로 끝나지 않는다.

최소한 아래 차원으로 막힘 지점을 남겨야 한다.

- flow
- step
- recovery_reason
- recovery_policy_level
- input_mode
- resume_action
- handoff 여부

이 기준은 나중에 `어느 단계에서 사용자가 가장 많이 막히는지`, `어떤 문구가 과도하게 fallback을 유발하는지`를 확인하기 위한 최소 관측 기준이다.

## 7. 구현 순서

1. UX baseline과 운영 정책을 문서에 먼저 고정한다.
2. step-aware fallback copy를 세분화한다.
3. 진행 상태와 현재 draft 요약 표면을 추가한다.
4. 버튼 단계와 텍스트 단계 문구를 분리한다.
5. retry 전용 copy를 첫 진입 copy와 분리한다.
6. handoff, manual review, resume 상태 UX를 보강한다.

## 8. 최종 요약

- 이 런타임은 자유 대화형 엔진이 아니라 guided structured interaction이다.
- UX 개편의 목적은 이 구조를 숨기는 것이 아니라 더 이해 가능하게 만드는 것이다.
- 사용자는 항상 `현재 단계`, `허용 입력`, `실패 이유`, `다음 행동`을 알아야 한다.
- unknown, retry, handoff, resume은 오류가 아니라 복구 UX의 일부다.
